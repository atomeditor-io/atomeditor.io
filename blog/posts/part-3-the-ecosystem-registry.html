The ecosystem registry — apm without atom.io

2026-09-13 · Part 3 of the chase log

Atom's package manager, apm, was built against one API endpoint: atom.io/api. When the site was sunset, those calls stopped answering — apm install minimap became a 301 to a blog post about the archive. Community packages and themes showed up empty in the install views.

The fix isn't another hosted service. It's a static registry generated from GitHub repositories.

How it works

The registry lives at atomeditor.io/api as plain JSON files, regenerated on a schedule from the atom-community catalog:

  • Browse/search — the full package list comes down as one JSON index (/api/packages, /api/themes), and apm search filters it locally instead of asking a backend.
  • Details — /api/packages/minimap returns full metadata exactly where apm view and apm install expect it.
  • Features — /api/packages/featured and /api/themes/featured mirror the old landing rows.
  • Tarballs — the dist.tarball for every version points straight at GitHub's codeload, so an install is a plain download from the repo itself: no proxy, no gatekeeper.

Because the whole thing is generated files in a GitHub-hosted site, it can't die like atom.io did — and it regenerates automatically from the repo catalog each week.

Native modules stay sane

The one thing a tarball can't guarantee is a working compile. Community packages with native addons get routed through the fork-chain rule: universal pre-N-API source, built against the Electron headers for whatever rung you're on. Everything compiles from source on CI — no stale prebuilt cache.

Compatibility with Pulsar's forward-ported packages is being used as a reference oracle: where a package has already been migrated, we adopt the port rather than reinventing it.

Broadly: install any package straight from GitHub source. No registry, no gatekeepers.
